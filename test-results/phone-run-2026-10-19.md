## FAILs in detail

### FAIL-1 CAMERA-06/07/08: any filter or Beauty gives a black live preview (OWNER PRIORITY)
Steps: Create -> swipe left on the preview or open Filters and tap Crisp / Golden Hour / Breeze (or turn on Beauty).
Expected: live preview with the filter. Actual: preview goes black and stays black (name label and UI still show). Selecting Normal (or Beauty off) brings the camera picture back immediately, so it is NOT "temporary": it is permanent while a filter is on.
Filter -> filter: stays black (the failing component is the same). Normal -> filter and Beauty both fail. Nothing flashes first: black from the first frame. A screencap of a GL surface can be black, but here the same screencap shows the normal preview (and the post screen thumbnails) fine, and logcat contains the error below on every attempt, so this is a real failure, not a capture artefact.
Logcat (cleared before each switch, `ReactNativeJS`):
`'camera:', 'java.lang.IllegalArgumentException: zq0: java.lang.IllegalArgumentException: PRIVATE format with resolution 1280x720 is not supported for ImageAnalysis on the device.` (stack: CameraX ImageAnalysis / SupportedOutputSizes)
Also repeated: `vu: Camera is not active` (harmless, fired on session restart) and `RNSkia: updateAndRelease() failed`.
Root cause: mobile/src/features/camera/FilteredCamera.tsx: `SkiaCamera` uses a frame output with the default Android pixel format `'native'` (= PRIVATE) and `targetResolution` 720x1280 (PREVIEW_RESOLUTION). On the Redmi M2010J19SI (Snapdragon, camera2 LIMITED) CameraX refuses PRIVATE at 1280x720 for the frame/analysis use case when combined with the 1080p video output, so the session never opens.
Not fixed: I could not verify a fix on the phone (it needs a new APK; I cannot build one here). Suggested fixes to try, in order: (1) pass `pixelFormat="yuv"` to `SkiaCamera` in FilteredCamera.tsx; (2) change PREVIEW_RESOLUTION to a size from the device's supported ImageAnalysis list (1280x960 / 1600x720 variants) or drop `targetResolution` and let CameraX pick; (3) catch onError in CameraScreen and fall back to the plain `<Camera>` (colour matrix applied only at export) so the user at least sees a picture. The Normal<->filter swap (`<Camera>` vs `<FilteredCamera>` with the same `video` output, CameraScreen.tsx ~264) is not the cause: filter->Normal recovers every time.

### FAIL-2 CAMERA-10: "Couldn't apply the filter" after recording with a filter
Steps: choose a filter (or leave one selected), record ~4 s, stop. Expected: "Applying filter..." then Post. Actual: alert "Couldn't apply the filter" with "Codec exception: CodecInfo{type=VideoDecoder ... mime=video/avc, bitrate=5756232, frame-rate=29.76, height=1920, width=1080 ... name=OMX.qcom.video.decoder.avc}", buttons Cancel / Post without filter.
Root cause (suspected): mobile/src/features/camera/videoFilter.ts / bakeColorMatrix: the Media3 Transformer fails to configure the Qualcomm AVC decoder on this phone for the 1080x1920 source. Not fixed. Post without filter works. Related to FAIL-1: filters are unusable on this phone end to end.

### FAIL-3 Recording race crash (FATAL, app dies)
Steps: Create -> tap Normal in the filter strip -> within ~1 s tap the red record button; wait ~6 s; tap the record button again.
Expected: one recording that stops. Actual: the app process dies ("FATAL EXCEPTION: com.margelo.nitro.recorder / java.lang.IllegalStateException: A recording is already in progress. Previous recordings must be stopped before a new recording can be started." at 17:36:56). The second tap called `start()` again because `recording` state is only set after `createRecorder` + `startRecording` resolve, and the camera was still re-starting after the Filtered->Normal swap, so that took > 6 s.
Root cause: mobile/src/features/camera/CameraScreen.tsx `start()` had no re-entrancy guard.
FIXED in working tree: added `starting` ref guard (`if (starting.current || recorder.current) return;`, cleared in `finally`, `recorder.current = null` on failure). Typecheck and eslint pass. Not verified on the phone (no new APK).

### FAIL-4 Map retest: "The map cannot be shown"
Steps: Discover -> map icon -> "Not now, just look at the map". Expected: real Google map. Actual: placeholder "The map cannot be shown / not available in this version".
Root cause (strongly suspected): mobile/src/features/map/mapConfig.ts `androidKeyConfigured()` reads `Constants.expoConfig.android.config.googleMaps.apiKey` (and the plugin entry). Expo strips `android.config` and `plugins` (they hold secrets) from the config embedded in the app, so this is always false at runtime on Android, whether or not the key is baked into the manifest, so `MAPS_AVAILABLE=false` and the map is never mounted. (If the CI secret GOOGLE_MAPS_ANDROID_KEY were missing the symptom would be identical: please check the secret as well.)
FIXED in working tree (needs a new build to verify): app.config.js now sets `extra.mapsKeyConfigured = !!process.env.GOOGLE_MAPS_ANDROID_KEY`; mapConfig.ts returns true when that flag is set. Typecheck and eslint pass.

## Front vs back camera quality (owner priority 2)
- App settings read in CameraScreen.tsx: `resolutionBias: video`, `fps: 30`, stabilization off, `targetBitRate` BIT_RATE (~6 Mbps), H.264 mp4, nothing differs between front and back. FilteredCamera's 720x1280 Skia preview only applies when a filter or Beauty is on (and currently crashes, FAIL-1); it does not feed the recorder.
- Measured (the app's own decoder error in FAIL-2 lists the recorded file's format): the recording made in the front-camera session was H.264 1080x1920, 29.76 fps, 5.76 Mbps, rotation 0. That is a normal 1080p30 recording at the configured bitrate. So the app is NOT picking a low-res format.
- I could not pull the files (app is not debuggable, cache is private, /sdcard path empty), so ffprobe on the file and a back-camera measurement were not possible; the back clip I posted was black/dark because the phone lies screen-up on the desk (back camera covers the desk), so back-vs-front sharpness could not be compared.
- Live preview of the front camera (screenshot during recording) was grainy and dim but that room was dim; with the Redmi front sensor (16 MP, binned) and 6 Mbps, softness is mostly the hardware and light, not the app. Conclusion: hardware/lighting-limited, plus possible modest gain from a higher bitrate (8-10 Mbps) for front.
